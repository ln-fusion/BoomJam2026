| 验证项 | 结论 | 阻断风险 |
|---|---|---|

## 2. 回溯：单对象历史缓冲

### 2.1 实现位置

| 类型 | 文件 | 职责 |
|---|---|---|
| `RewindSnapshot` | `Assets/Game/Runtime/Gameplay/Rewind/RewindHistory.cs` | 单 Tick 的状态快照（位置/旋转/速度/角速度） |
| `RewindHistory` | 同上 | 固定容量环形缓冲，按 Tick 采样与查询 |
| `IRewindableState` | `Assets/Game/Runtime/Gameplay/Rewind/IRewindableState.cs` | 目标状态的读写端口 |
| `RewindAbilityRuntime` | `Assets/Game/Runtime/Gameplay/Rewind/RewindAbilityRuntime.cs` | 采样、触发、冷却、重置 |

`EntityId` 为新增的 Foundation 强类型 ID（`Assets/Game/Runtime/Foundation/EntityId.cs`），
设计文档 6.7 要求所有影响结果的集合遍历按稳定实体 ID 排序，此类型是该约束的载体。

### 2.2 容量与内存上限计算

回溯时长与容量关系：

```text
容量 = 回溯秒数 × Tick 频率 + 1
```

60 Hz 下按不同回溯时长：

| 回溯时长 | 快照数 | 单对象内存 |
|---:|---:|---:|
| 1 秒 | 61 | 约 2.0 KB |
| 3 秒 | 181 | 约 5.8 KB |
| 5 秒 | 301 | 约 9.6 KB |

单快照的托管布局：

```text
long  Tick            8 字节
Vector2 Position      8 字节（2 × float）
float RotationDegrees 4 字节
Vector2 LinearVelocity 8 字节
float AngularVelocity 4 字节
合计                 32 字节
```

加上数组对象头（约 24 字节）与字段填充，实测按每个快照 32 字节、每个缓冲额外
约 56 字节的对象开销估算。

**能力框规模下的总量**：设计文档未固定同屏能力框数量上限，按关卡容量上限的
典型量级（数十个）估算：

| 能力框数量 | 3 秒历史总量 | 判定 |
|---:|---:|---|
| 20 | 约 116 KB | 无压力 |
| 40 | 约 232 KB | 无压力 |
| 100 | 约 580 KB | 仍可接受 |

**结论**：不需要对象池、分块存储或快照压缩。历史上限由关卡编辑器「回溯时长」
字段控制，编译期应校验 `回溯秒数 × Tick 频率 + 1 <= 缓冲容量`，防止配置越长
越慢的隐式退化。

**建议**：`RewindHistory` 容量在构造时固定（当前实现），因此校验必须在世界构建
阶段完成——配置非法时拒绝开始模拟，而不是运行时静默截断。这与设计文档 6.4
「开始前权威校验」的既有策略一致。

### 2.3 状态可序列化性判定

设计文档 6.8 风险条目要求确认「对象状态是否可序列化」，否则需限制可回溯目标白名单。

**判定：可序列化，无需白名单限制。**

依据：

1. 回溯只覆盖**四个物理量**（位置、旋转、线速度、角速度），全部是 `float`/`Vector2`
   这类值类型，无引用、无 Unity 对象。
2. 接触对、关节、Sleep 状态属物理引擎内部状态，**刻意不保存**。设计文档 6.5 已确立
   「不要尝试只把 Transform、速度写回初值」的原则，原因是这些内部状态会残留；
   但该原则针对的是**整个世界重建**，而回溯是**单对象局部恢复**——残留的接触对
   会在下一 Tick 由物理引擎自动重算，因此不构成阻断。
3. 触发「清除接触影响」的诉求由 `ITeleportable.DetachFromZones` / 回溯写入后的
   重新检测承担，不依赖保存物理内部状态。

**唯一需要调用方遵守的约束**：`IRewindableState.Restore` 必须直接写刚体字段，
不得使用 `Rigidbody2D.MovePosition` 或逐帧 `Transform` 赋值——前者会与物理步进
耦合产生额外插值，后者会绕过物理引擎导致碰撞体位置与刚体位置不一致。

### 2.4 触发语义

回溯是**进入触发一次**，不是持续生效；这与加速等持续型能力不同，因此
`RewindAbilityRuntime` 刻意**不**实现 `IAbilityRuntime`，C41 再按能力框框架接入。

冷却（`cooldownTicks`）用于防止对象停留在回溯框内时每 Tick 连续回溯。实测语义：

- 冷却按**对象**隔离，一个对象冷却不阻塞另一个对象。
- 冷却期内触发返回 `false` 且**不触碰目标状态**。
- 历史不足（回溯时长超过已积累历史）时取**最旧可用快照**而非失败——这与
  C41「越界配置安全截断」一致。

## 3. `IRewindableState` 接口草案

```csharp
public interface IRewindableState
{
    RewindSnapshot Capture(long tick);
    void Restore(in RewindSnapshot snapshot);
}
```

**设计取舍**：

- **不暴露 `Rigidbody2D`**：接口只交换值类型快照，因此可在 EditMode 下用假目标
  完整测试，不需要真实物理场景。C20 的 8 个回溯测试全部基于假目标通过。
- **不包含 Tick 校验**：`Capture` 接收 tick 但由调用方保证单调递增，
  `RewindHistory.Record` 不做重复 Tick 检测。理由：Tick 单调性由
  `SimulationLoop` 统一保证（设计文档 6.6），在此重复校验是冗余。
- **`Restore` 使用 `in` 参数**：快照 32 字节，`in` 避免复制；也向实现方表达
  「不得修改传入快照」的意图。

**C40/C41 需要补充的部分**：

- 真实实现（挂在 `Rigidbody2D` 所在对象上）。
- 环形缓冲的**固定 Tick 采样时机**——按设计文档 6.6，应在
  `AbilityPostPhysicsTick` 阶段采样，保证记录的是物理推进后的稳定状态。
- `IRewindHistory` 作为独立接口暴露给能力框（当前 `RewindHistory` 是具体类型，
  C40 若需要多目标共享或替换存储策略再抽接口）。

## 4. 传送：重复触发与嵌入保护

### 4.1 实现位置

| 类型 | 文件 | 职责 |
|---|---|---|
| `PortalPair` | `Assets/Game/Runtime/Gameplay/Portals/PortalRuntime.cs` | 一对传送门的端点与朝向 |
| `PortalRuntime` | 同上 | 配对注册、传送、冷却、出口探测 |
| `IPortalExitProbe` | 同上 | 出口可用性探测端口 |
| `ITeleportable` | `Assets/Game/Runtime/Gameplay/Portals/ITeleportable.cs` | 目标位置/速度读写端口 |

### 4.2 三类边界问题的对策

**（1）乒乓触发**

问题：传送后对象通常与出口门重叠，下一 Tick 立即再次触发反向传送，形成无限循环。

对策：传送成功后给**该对象**记录冷却截止 Tick（默认 2 Tick），冷却期内任何门
都不再接受它。冷却按对象隔离，不阻塞其他对象。

判定：**已解决**。这是与回溯冷却同一套机制，实测通过。

**（2）嵌入**

问题：出口位置若落在静态碰撞体内，对象会被物理引擎挤出并产生非预期速度，
表现为「传送后乱飞」。

对策：传送**前**通过 `IPortalExitProbe.IsExitAvailable` 询问出口是否可放置。
不可用时返回 `Blocked` 并**保持对象在原位与原速度**，由玩家调整布局。

判定：**接口与失败语义已就绪**，真实探测器待 C39 用
`PhysicsScene2D.OverlapBox`（排除自身碰撞体）实现。选择「放弃传送」而非
「强行放置」的理由：强行放置会让对象嵌在墙里，物理引擎的挤出方向不可预测，
比不传送更难调试。

**（3）重叠门/连续门**

问题：同一 Tick 内多个门命中时，结果依赖遍历顺序。

对策：一次触发只处理**一个** PortalId，由调用方按 PortalId 升序取第一个命中。
`PortalRuntime` 内部用 `StringComparer.Ordinal` 字典，`TryRegister` 拒绝重复
PortalId，保证「未知/重复 PortalId 构建校验失败」（C38 验收项）。

判定：**已解决**。构建期校验入口已具备（`TryRegister` 返回 false），C38 只需
在编译校验中把该返回值转为用户可见错误。

### 4.3 速度映射规则

出口朝向与入口朝向的差决定速度旋转：

```text
radians = (exitForwardDegrees - entranceForwardDegrees) × π / 180
velocity' = rotate(velocity, radians)
```

实测语义：速度**大小守恒**，方向按朝向差旋转（测试覆盖 0° → 90° 情形）。
位置**直接设为出口坐标**（不做沿法线偏移）。偏移量的选择留给 C39，因为
「偏移多少」取决于门体厚度与对象碰撞体尺寸，属表现与物理参数的耦合，
提前固定会限制后续调整。

### 4.4 `ITeleportable` 接口草案

```csharp
public interface ITeleportable
{
    Vector2 Position { get; }
    Vector2 Velocity { get; }
    float ForwardDegrees { get; }
    void ApplyTeleport(Vector2 position, Vector2 velocity);
    void DetachFromZones();
}
```

**`DetachFromZones` 的必要性**：出口若落在另一个范围框（如加速框）内，该框会在
下一 Tick 观察到一次「进入」并施加效果。若传送前不把实体从各框的占用集合中
移除，这个「进入」事件在语义上是假的——对象并没有穿过那个框的边界。传送前
解除占用、传送后由各框重新检测，是唯一能保证占用集合与实际位置一致的顺序。

## 6. 未完成项与剩余风险

**本周期未执行**：

- Unity 侧编译与测试运行（本机 Unity 未启动）。交付前必须在 Unity 中执行
  EditMode 全量测试，确认新增 8 个回溯测试与 6 个传送测试通过。

  的接触重算行为」尚未实测。**这是主要剩余风险。**

**剩余风险与缓解**：

| 风险 | 影响 | 缓解 |
|---|---|---|
| 回溯写入后接触对未及时重算 | 对象可能短暂穿墙或被弹开 | C41 实现真实 `Restore` 后立即用 Golden Case 验证；必要时在写入后显式唤醒刚体 |
| 出口偏移量需与门体厚度耦合 | C39 可能需要调整传送落点 | 已刻意不在本周期固定偏移，保留调整空间 |
